**Current state (2026-07-21):** SM90 BF16 GEMM module (from Kota's handoff, `src/level3/batched_gemm/BF16/SM90/`) is wired into the top-level dispatcher and validated on real H200: 37/37 correctness at `0.00e+00` MaxRelErr, several large shapes hitting 90-96% of cuBLAS throughput. See [[project_active_repo]] for which repo this actually lives in.

**setmaxnreg register-split is intentionally REMOVED, not just unused** — the kernel used to call `setmaxnreg.dec`/`.inc` (Hopper's warp-specialized register-reallocation instruction, giving the TMA-only producer warpgroup fewer registers and the wgmma consumer warpgroups more) with values (`PRODUCER_REGS=72`, `CONSUMER_REGS=240`) that never actually worked — ptxas silently ignored them and fell back to uniform allocation the whole time. Confirmed via real H200 SASS/ncu/nsys captures that removing the dead calls changed nothing (register counts, occupancy, instruction counts, kernel duration all matched original within noise).

**Why it didn't work, if picked up again:** `setmaxnreg` requires an EXACT equality — `PRODUCER_REGS + num_consumer_warpgroups * CONSUMER_REGS == baseline_registers_per_thread * total_warpgroups` — confirmed via `NVIDIA/cutlass` GitHub issue #2007 (maintainer thakkarV). The baseline is whatever ptxas naturally compiles that SPECIFIC kernel's code to — not portable from CUTLASS or anywhere else (tested CUTLASS's own canonical 40/232 directly against this kernel, still failed). This kernel's two tile shapes have genuinely different baselines (126 vs 167 registers/thread) sharing one compilation unit, so a single register-split value can't satisfy both — would need per-shape values and likely separate compilation units (`--maxrregcount` is silently overridden by an explicit per-kernel `__launch_bounds__`, so it can't differentiate the two shapes in one TU).

**Explicit user decision: leave it out for now, but this is a real future task, not closed.** Full methodology (the autotuning sweep script, the exact equations, the CUTLASS reference values, why they didn't transfer) is documented in `cublas_rev_eng_binary/analyzations_h200.md` §H2.7-H2.9 — read that before attempting this again rather than re-deriving from scratch. Also worth checking first: SASS already proved ZERO register spilling in this kernel under uniform allocation, meaning the classic motivating case for this optimization (avoiding spills) may not clearly apply to these specific (128x256, 128x128) tile shapes — the real payoff might be small here regardless of getting the math right. Same open opportunity exists for SM103 (Blackwell CUTLASS kernels use this too, with their own 48/256 values, also not portable) — see [[project_sm103_cuh_locked]].

**Two things confirmed when the user asked to reconsider doing this immediately (still deferred, decision re-confirmed):** (1) "one universal value for every shape" doesn't work here — CUTLASS's own kernel looks universal (one fixed 40/232 across its whole tile catalog) but only works because their heavier CuTe abstraction keeps the natural baseline clustered near ~168 regardless of tile size; Kota's leaner kernel's baseline visibly scales with tile size instead, so it needs a value per shape, confirmed as arithmetic (378 vs 501 required, not satisfiable by one pair) not a tuning gap. (2) ptxas's "silently ignore and fall back to uniform" behavior is NOT unconditionally safe — CUTLASS issue #2007 shows a near-miss register value caused an actual hang at runtime, not just a no-op. Any future per-shape sweep must validate every candidate by actually RUNNING it on hardware (hang + correctness check), not just by confirming the compile-time warning disappeared.

**UPDATE 2026-09-26: PORTED TO THE TEAM REPO** (lib 97735ad). These fixes were never committed to BlubridgeAI/Tensor-Implementations until then; see [[project-reduction-fixes-pushed-0926]].

Work in `master_gau_latest_sm_86_RTX_3060` (RTX 3060 / sm_86) reduction kernels, June 2026.

**Fixed & validated (vs brute-force + torch.sum, CPU+GPU, sum/mean/max, f32/f16/bf16):**
- **Bug #1 middle-axis (`outer>1`)**: layout made a 3-part (outer,reduced,inner) decomposition with `input_outer_stride` but consumers ignored it (only correct when outer==1). GPU: dropped `num_outputs` clamp + remap output_idx→slab base in OuterContiguous kernel (threaded `outer_stride`). CPU: added `cpu_demote_middle_to_generic()` in ReductionImpl.h, called at all 6 CPU layout sites — middle uses the correct Generic carry-add path (GPU keeps fast OuterContiguous).
- **Bug #2 InnerContiguous GPU (last-axis)**: `block_x_reduce` was 1-D-block code on 2-D blocks (hardcoded shuffle offset 16, shared indexed by wid only, touched shared when size==0). Rewrote to PyTorch structure. Op-agnostic.

- **Bug #3 GPU non-consecutive multi-axis (e.g. `sum(dim={0,2})`)**: FIXED. Generic GPU path was running with EMPTY OffsetCalculators + num_outputs/reduced_count=0 (clamped to 1). Added `setup_generic_path()` helper in ReductionImplGPU.cu, called in all 4 GPU dispatchers: sets num_outputs/reduced_count and builds output_calc (non-reduced dims) + input_calc (reduced dims) from input's real strides. Kernel already did `src[out_base+in_off]`. Validated sum/mean/max on {0,2},{1,3} vs torch + brute force.

All 3 reduction bugs now fixed & validated in master_gau_latest_sm_86_RTX_3060 (37/37 sum sweep, 33/33 vs torch, 26/26 ops×dtypes). Uncommitted.

**Bug #4 FIXED in BBP (was thought to be "2 opt bugs", actually ONE root cause):** `block_y_reduce` lacked a TRAILING `__syncthreads()`. BBP's vec4 kernel (and the multi-CTA combine tail) call block_y_reduce ONCE PER OUTPUT LANE reusing the SAME shared buffer; with no trailing barrier, ty!=0 threads raced ahead to the next lane and overwrote smem while ty==0 was still reading → every lane corrupted except the LAST (signature: lane 3 correct, lanes 0-2 wrong, 3/4 of outputs bad). Manifested as [1024,1024] axis=0 (bias-grad shape) wrong on sm_86. Fix = add `__syncthreads()` at end of block_y_reduce (ReductionKernels.cuh ~L405). After fix: BBP sum 37/37, ops 26/26, torch 33/33, [1024,1024]ax0 exact. **VALIDATED ON THE ACTUAL Ada/sm_89 SERVER (10.101.0.203, /mnt/volgrp03/.../gautam_new_best_precision) — reduction_fix_tests.cpp: 54/54 PASS.** So all 4 fixes are arch-independent (confirmed sm_86 AND sm_89). Combined one-file test = BBP/Tensor-Implementations/reduction_fix_tests.cpp (no torch dep, brute-force reference). Found via bisection probe (vec4 needs num_outputs>=128; bug needs block_y active i.e. reduced>=~64) + the "last-lane-correct" tell. NOTE other trees (sm86 etc.) only have this bug IF they have the vec4 kernel / call block_y_reduce per-lane; the trailing sync is harmless to add everywhere.

**(superseded) earlier mistaken framing — 2 pre-existing opt bugs in BBP:** the leading-axis OuterContiguous `[1024,1024] axis=0` is wrong on sm_86 (GPU vs CPU=torch). Isolated via experiments: vec4-ON+mcta-OFF fails, vec4-OFF+mcta-ON fails, BOTH-OFF (base scalar block_y path) = CORRECT → vec4 and multi-CTA are EACH independently broken on sm_86. Deterministic (compute-sanitizer racecheck & initcheck CLEAN; fails under serialized sanitizer). Ruled out: race, uninit, float4 misalignment (offsets are multiples of 4), missing inter-lane __syncthreads (tested, no change). Deep PyTorch Reduce.cuh comparison: BBP matches PyTorch on get_output_vec_size decision EXCEPT BBP hardcodes vec4 (no alignment/divisibility check), and matches on ctas_per_output/staging/combine/input-tiling. Needs on-GPU printf instrumentation to pin. Likely sm_86-only (ctas_per_output/occupancy differs on sm_89 where they train); bias-grad may use dedicated reduce_bias_kernel anyway. Not yet propagated to other folders.

**GPT-2 bias-grad WAS affected by bug #4 (corrected — earlier "unaffected" claim was WRONG).** Real path: `nn::Linear::forward` uses `autograd::addmm(bias,input,weight)` → `AddmmBackward` does bias-grad via `reduce_sum(grad_out,{0})` → **`unified_reduce_kernel_outer_vec4`** (vec4). The dedicated `cuda_linear_bias_backward`/`reduce_bias_kernel` (LinearBackward.cpp:107) is DEAD CODE for this model (LinearBackward bias branch never fires; bias rides in addmm). Confirmed by nsys on the RTX 6000 Ada / sm_89 training server: `unified_reduce_kernel_outer_vec4<float,float,SumOp>` ran 15,680×. Bias shapes `[B*T=16384, F]` ax0 → F∈{768,2304,3072} (fp32, %4==0, ≥128, leading-axis → vec4+block_y+multi-CTA). **On the sm_89 server: buggy kernel → bias-grad maxerr ~300 (3/4 lanes wrong); fixed → ~5e-5.** So pre-fix GPT-2 runs had corrupted bias-grads on Ada — bug is NOT sm_86-only, the race fires on sm_89 too. (User's earlier "PyTorch bias-grad matched" likely predates vec4: vec4+multi-CTA were uncommitted perf work on top of BBP HEAD, which has NO vec4 kernel.) Final regression = `reduction_final_test.cpp` (87 cases: real bias shapes, vec4 gate edges, multi-CTA stress, ops, dtypes; fp16 tol scales w/ sqrt(reduced); GPU-vs-CPU guard) — **87/87 on sm_86 AND sm_89.**

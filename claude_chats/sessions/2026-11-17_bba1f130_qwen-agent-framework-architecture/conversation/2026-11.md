## Short answer

- **Qwen-Agent is written entirely in Python.** It has no C++ core, no Python bindings, no CUDA and no GPU kernels.
- **It does not train a model and does not run the model's math.** It runs on top of a model that is already trained and already running in a separate server, such as vLLM, Ollama or Alibaba's DashScope cloud.
- **What it does:** it builds the prompt with the list of tools and sends it to the model over HTTP. It reads the text that comes back and finds the `<tool_call>` part. It runs that tool as ordinary Python, puts the result back into the chat, and asks the model again. This repeats until the model stops calling tools.
- **Learned or rules? Both.** The model learned to write `<tool_call>{...}</tool_call>` during the Qwen team's own post-training. Qwen-Agent only writes that format into the prompt and reads it back out of the reply. Actually running the tool is Python code in Qwen-Agent; the model only writes text.

## Where it sits compared to PyTorch

```
Layer 4  Agent framework     Qwen-Agent, LangChain, ...       pure Python: prompts, tool loop, parsing
             |  HTTP request (OpenAI-style JSON)
Layer 3  Inference server    vLLM, SGLang, Ollama, DashScope  <- GPU kernels run here (GEMM, attention)
             |  loads
Layer 2  Trained weights     e.g. Qwen3-8B .safetensors
             |  produced by
Layer 1  Training framework  PyTorch / TensorFlow / Megatron  <- C++/CUDA core + Python bindings, autograd
```

PyTorch and TensorFlow are layer 1, and inference servers in layer 3 are built on them too. Qwen-Agent is layer 4. It never touches a tensor in its normal path.

## What the agent framework actually does

**1. Tools are Python classes** (`qwen_agent/tools/base.py`):
- `BaseTool` (line 109) has a `name`, a `description`, `parameters` given as a JSON schema, and a `call()` method.
- `@register_tool` adds the class to a plain dictionary, `TOOL_REGISTRY` (lines 24 and 44-55).
- The schema is checked with `jsonschema` (lines 87-101).
- Built-in tools: `code_interpreter`, `web_search`, `retrieval`, `doc_parser`, `image_gen`, `amap_weather`, `mcp_manager`, `python_executor` and others.

**2. The tool list is turned into prompt text.** In `qwen_agent/llm/fncall_prompts/nous_fncall_prompt.py:254-266`:
```
# Tools
You may call one or more functions to assist with the user query.
You are provided with function signatures within <tools></tools> XML tags:
<tools>
{tool_descs}
</tools>
For each function call, return a json object with function name and arguments within <tool_call></tool_call> XML tags:
<tool_call>
{"name": <function-name>, "arguments": <args-json-object>}
</tool_call>
```

**3. The reply is parsed as text** (same file):
- line 157: `item_text.split('<tool_call>')`
- line 192: `split('</tool_call>')`
- line 214: `json5.loads(...)` reads the tool name and arguments.

**4. The loop.** This is the whole agent, in `qwen_agent/agents/fncall_agent.py:73-108`, shortened:
```python
num_llm_calls_available = MAX_LLM_CALL_PER_RUN          # 20 by default (settings.py:24)
while num_llm_calls_available > 0:
    num_llm_calls_available -= 1
    output = self._call_llm(messages, functions=[...tool schemas...])   # HTTP call to the model
    messages.extend(output)
    used_any_tool = False
    for out in output:
        use_tool, tool_name, tool_args, _ = self._detect_tool(out)      # did the text contain <tool_call>?
        if use_tool:
            tool_result = self._call_tool(tool_name, tool_args)          # runs the Python call()
            messages.append(Message(role=FUNCTION, name=tool_name, content=tool_result))
            used_any_tool = True
    if not used_any_tool:
        break                                                            # model answered without a tool -> done
```

The loop stops in one of two ways:
- the model replies without a tool call, or
- 20 model calls have been used up.

**Other parts, all Python:** RAG (BM25 search over documents), memory, multi-agent groups, a Gradio web UI and an MCP client.

## About "kernels"

There are no GPU kernels. The word "kernel" does appear in `qwen_agent/tools/code_interpreter.py`, but there it means a **Jupyter kernel**: a separate Python process that runs the code the model wrote.
- line 43: `from ipykernel import kernelapp as app`
- lines 126-138: it starts one kernel per agent, inside a Docker container, and records the container id.

That is a process, not a CUDA kernel.

## Did the model "learn" tool calls?

**Model side, learned in training.** I opened Qwen3-8B's own `tokenizer_config.json` from Hugging Face:
- Its chat template has **the same text, word for word**: `# Tools ... <tools></tools> ... <tool_call>{"name": ..., "arguments": ...}</tool_call>`.
- `<tool_call>`, `</tool_call>`, `<tool_response>` and `</tool_response>` are **special tokens in the model's vocabulary**.

So the format is built into the model's own files, which shows the Qwen team trained it on this format during post-training. That training code is **not** in Qwen-Agent. A search of the whole repo for `.backward(`, `torch.optim`, `zero_grad` and `Trainer(` finds **0 hits**.

**Framework side, rules in code.** Qwen-Agent writes the prompt in that format, parses the reply, checks the JSON, runs the tool, sends the result back and enforces the 20-call limit.

**The parsing can also move to the server.** README lines 82-83:
- For Qwen3-Coder, they say to let vLLM parse tool calls (`--tool-call-parser`).
- For Qwen3 and QwQ, they say **not** to, because Qwen-Agent parses the replies itself.

## PyTorch/TensorFlow vs Qwen-Agent

| | PyTorch / TensorFlow | Qwen-Agent |
|---|---|---|
| Language | C++/CUDA core + Python bindings | Python only (0 C/C++/CUDA files) |
| Works on | tensors | chat messages (text, JSON) |
| GPU kernels | yes (GEMM, attention, ...) | none |
| Training (autograd, optimizers) | yes | none (0 hits) |
| Runs the model's math | yes | no: sends an HTTP request (or calls HF `generate()` on the optional path) |
| Main dependencies | CUDA, cuBLAS, cuDNN | `openai`, `dashscope`, `requests`, `json5`, `pydantic`, `jsonschema` |
| Output | weights, logits | a final answer after a loop of model calls and tool runs |

**What this means for our work:** nothing in Qwen-Agent would use or change our kernels or BluTrain. The one link is the data format. If we SFT a model and want it to work with Qwen-Agent, the SFT data has to use this exact `<tool_call>` / `<tool_response>` format and its special tokens.

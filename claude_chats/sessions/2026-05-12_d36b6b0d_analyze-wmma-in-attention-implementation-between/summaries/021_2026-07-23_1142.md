2. Key Technical Concepts:
   - PEP 668 externally-managed-environment, `--break-system-packages`, `--ignore-installed` for debian-vs-pip package conflicts
   - Bash relative-path resolution pitfall: `${BASH_SOURCE[0]}` resolving wrong after a `cd`
   - CUTLASS kernel generator rewriting `.cu` files at `cmake` configure time (breaks incremental `make` if configure re-runs)
   - `-arch=sm_90a` shorthand vs explicit `-gencode arch=compute_90a,code=sm_90a` (shorthand doesn't reliably carry the "a" suffix to the PTX virtual arch on all toolkits)
   - `cuLibraryLoadData` — CUDA driver API for runtime-loaded fatbins; explains why cuBLASLt's real `nvjet_*` Hopper kernels are invisible to `cuobjdump`'s static ELF scan
   - `ncu --page source --print-source sass` — captures SASS for whatever kernel actually runs at profiling time, independent of load mechanism (the replacement for the entire `cuobjdump`-based `extract_kernel_sass.sh` approach, which was deleted)
   - `/proc/<pid>/maps` inspection as a reliable way to resolve a lazily-`dlopen`'d library's real path (replacing `ldd`, which can't see lazy-loaded libraries)
   - `rsync -avz --progress` for resumable large binary transfer, explicitly chosen over `scp` and explicitly NOT git/GitHub
   - `ncu --import <file>.ncu-rep --csv` — converts binary ncu reports to readable CSV locally, no server access needed
   - Kernel-name naming convention decode: `nvjet_sm90_tst_<TILE_M>x<TILE_N>_<K_TILE>x<STAGES>_<CLUSTER_M>x<CLUSTER_N>_<h|v>_bz_[schedule]_<LAYOUT_SUFFIX>` — tile shape (HIGH confidence), K-tile/pipeline-stages (HIGH-MEDIUM), cluster shape (HIGH, confirmed via real SASS `S2UR SR_CgaCtaId`/`UCGABAR_ARV`), h/v (pattern proven 100% via `v` iff cluster's 2nd axis==1; meaning still medium-confidence, best guess = CUTLASS's RasterOrder), `bz` (LOW-MEDIUM, unresolved), `coopA`/`coopB`/`splitK`/plain (scheduling variants, cleanly tile-shape-separated), trailing `TNT`/`TNN` (NOT the outer transpose mode — an internal cuBLAS detail)
   - `HGMMA` — the real disassembled SASS mnemonic for Hopper's `wgmma.mma_async` BF16 tensor-core instruction (a real correction from an initial wrong assumption of `WGMMA`/`HMMA`)
   - `LDL`/`STL` SASS instructions as the direct, unambiguous register-spill indicator (more reliable than ncu's `local__load_bytes.sum`/`local__store_bytes.sum` metrics, which reported `"n/a"` literally rather than a numeric zero)
   - `USETMAXREG.TRY_ALLOC.CTAPOOL` — Hopper register-reallocation instruction, consistent with the constant 168 registers/thread found across all 18 variants
   - CUTLASS `cute::GMMA::Major::{MN,K}` — smem operand layout modes; `Major::K` (K-contiguous) is the "easy" case our existing NT path already implements; `Major::MN` needed for NN's B and TN's A/B
   - `cute::SM90::GMMA::make_gmma_desc<MajorMode>(tensor)` — the actual descriptor-construction function; has a `static_assert` requiring a canonical K-width per call (`256/sizeof_bits(T)` = 16 elements for dense bf16) — this assert fails if you try to build ONE descriptor spanning a whole `BK`-wide tile; it must be called per 16-element-wide `k_block` slice
   - `ss_smem_selector<Major, ElementType, BLK_MN, BLK_K>()` (in `cutlass/gemm/collective/builders/sm90_common.inl`) — picks the correct smem swizzle atom (`Layout_MN_SW128_Atom` etc.) given tile dims; only checks `BLK_MN0 % 8`/`BLK_K0 % 8`, does NOT itself enforce the 16-element canonical K-width (that only surfaces in `make_gmma_desc` itself) — a real trap I initially fell into (first probe passed but was insufficient proof)
   - `local_tile(tensor, Shape<_128,Int<16>>{}, make_coord(0, K_BLOCK))` — the correct CUTE idiom for slicing a full smem tile into per-k_block 16-wide pieces before calling `make_gmma_desc`
   - Real derived descriptor constants for a 128×64 MN-major bf16 tile, per 16-wide k_block: `leading_byte_offset=64`, `stride_byte_offset=128`, `layout_type=1` (B32 swizzle), identical across all 4 k_blocks (only base address differs at runtime)
   - CUTLASS's real cooperative-vs-pingpong schedule selection rule (`sm90_gmma_builder.inl` line 1020-1022): `size<0>(TileShape_MNK{}) == Int<64>{}` picks Pingpong, otherwise Cooperative — i.e. the real constraint is just `M >= 128` with `M==64` as the sole special case; **no `M % 128 == 0` requirement exists in CUTLASS** — confirming our own codebase's stricter assert is artificial
   - `wgmma` m64 atom — the real, fixed hardware granularity (64 rows); since 320 = 5×64 (clean), the correct general fix is `BM % 64 == 0` (not `%128`) plus uneven atom distribution across the 2 fixed consumer warpgroups (e.g. 320/64=5 atoms → 3+2 split)
   - `nvcc` cross-compilation for `sm_90a` works without a physical Hopper GPU present (confirmed: local machine has only an RTX 3060, Ampere/sm_86, yet all probes compiled/failed correctly for sm_90a); `make_gmma_desc` is `CUTE_HOST_DEVICE constexpr`, so a plain host executable (no kernel launch) can compute and print its real byte-offset values directly on CPU, with only the address-cast portion (`cast_smem_ptr_to_uint`) failing harmlessly at host runtime
   - BluBLAS's existing SM90 module file structure (`Bgemm_sm90_warpspecialized_template.cuh` shared template + `Bgemm_sm90_{nn,nt,tn}_variants.cu` thin per-layout wrapper files + `Bgemm_sm90_dispatcher.cu` + `Bgemm_sm90_bf16.cuh`) already matches the SM103-style separation the user asked about — confirmed directly from the file listing, no restructuring needed
   - `Sm90WarpspecConfig<_BM,_BN,_BK,_LOAD_PIPE_DEPTH=0>` template struct — current hardcoded constraints: `NUM_CONSUMER_WARPGROUPS=2` (fixed), `static_assert(BM % 128 == 0)`, `static_assert(BN == 128 || BN == 256)`, `static_assert(BK == 64)`
   - `Sm90SmemLayout<Config, Layout>` — layout-aware smem/pipeline-depth calculator; already has a `RAW_PIPE_DEPTH` auto-derivation (tries 2/double-buffered, falls back to 1/serialized if smem-constrained) for the raw-transpose staging buffers used by NN's B and TN's A/B — this fallback-to-1 case is the documented root cause of the "NN/TN measured 13-19x slower than NT" performance gap
   - `transpose_to_kmajor_swizzled()` — the current software workaround: loads MN-major operand raw (no swizzle) via TMA, then transposes it in shared memory into K-major-swizzled layout via a per-thread XOR-swizzle formula, so downstream wgmma-issue code stays layout-agnostic; this is exactly what the proposed native-MN-major-descriptor fix would eliminate entirely
   - `make_gmma_desc_k_major<RowStrideElems, SwizzleBytes>(addr)` — our own current hand-rolled K-major-only descriptor builder (bit-position formula independently derived, matches CUTLASS's `GmmaDescriptor` bitfield layout: `start_address_[16:30)`, `leading_byte_offset_[16:30)`, `stride_byte_offset_[32:46)`, `layout_type_[62:64)`)

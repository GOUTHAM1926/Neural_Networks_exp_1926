## 2. Key Technical Concepts

- SM90 warp-specialized Hopper GEMM: producer/consumer warpgroups, TMA, wgmma, mbarriers, thread-block clusters
- `Sm90WarpspecConfig<...>` — 51 template params; rebinders `Sm90NcwRebind`, `Sm90SplitKRebind`, `Sm90EpiSwzRebind`, `Sm90LateWaitRebind`, `Sm90RasterRebind`, `Sm90RegSplitRebind`
- `namespace blublas_ws` = OUR kernels (`ws` = warp-specialized); bare `bgemm_sm90_kernel` = Kota's; `nvjet_*` = cuBLAS. The definitive discriminator in nsys traces.
- `MATOMS = BM/64`; `SPLIT_M = (MATOMS % NCW == 0)`. At BM=64, MATOMS=1, so NCW=2 forces an N-split → half-width wgmma (WGMMA_N=64 instead of 128).
- CUTLASS Cooperative vs Pingpong schedules: Cooperative = 2 warpgroups split one tile's M, requires TileShape_M ≥ 128, falls back to Pingpong at M=64. **We have no Pingpong.**
- coopA/coopB = tile-shape tag in cuBLAS nvjet names, NOT multicast, NOT the CUDA Cooperative Groups API
- Kota's `sm90_tn_splitk_plan(M,N,batch)` — a hardcoded 6-row table keyed on `(grid_m, grid_n)` where `grid_m=ceil(M/128)`, `grid_n=ceil(N/64)`
- Shape formula: M = B·T for nn/nt; K = B·T for tn. `GRAD_ACCUM = global_batch/(B*T*world_size)` — global_batch changes only the loop count, never a shape.
- Trainer memory model: ZeRO-1 shards optimizer state only; activations are per-rank and do NOT shard
- H200: 141 GB HBM3e, 4.8 TB/s memory bandwidth, NVLink 900 GB/s, ~60 MB L2, 228 KB smem/SM, 700 W cap, 132 SMs, max IPC 4/SM
- ncu counter classes: `sm__sass_thread_inst_executed_op_{integer,uniform,memory,control,bit,conversion,misc,fp16,ffma,...}_pred_on`; `smsp__inst_executed_pipe_*`; the FMA pipe also executes IMAD
- Power measurement protocol: `power.draw.instant` (not `power.draw`, a 2.4 s trailing average); 2 Hz (100 Hz aliases); persistence mode on; 40 s windows with 8 s discarded; lock low enough that the cap never activates; verify the lock held

2. Key Technical Concepts:
   - **Vj2 backward before the change:**
     - One block = 128 keys of one chat for ONE query head.
     - Two compute groups (group 0 = keys 0-63, group 1 = keys 64-127).
     - Producer warp 0 = loader (TMA Q, dO, LSE, D per 64-row step). Warp 1 = dQ writer (fp32 bulk reduce-add into the accumulator). A conversion kernel turns dQ into bf16.
     - Each query head writes bf16 dK/dV partials, which 2 head-sum (greduce) kernels add up.
   - **Idea 1:** group 1 skips the fully masked first step. It writes zero dS rows, syncs at BAR_PDS, runs its dQ GEMM for columns 64-127, then stores directly or hands off.
   - **Idea 2:** direct bf16 dQ for a chat's first 2 query tiles (`nDirect`). The dq_tiles `.w` field marks direct tiles; the prep kernel skips zeroing them and the convert kernel skips them.
   - **Idea 4 (HSUM template flag):**
     - One block per (128-key tile, KV head), running NT = G × nIter steps.
     - The loader, writer and both groups count steps across heads (`ii` = step in head, `g` = head offset, `hst` = slot stride).
     - fp32 dK/dV are kept in registers and the final rows are written at `b*Hkv + hkv`. No partials, no greduce.
     - A `pend` flag tracks a hand-off still pending; G == 1 uses the per-head list.
   - **Rule 1:** sections of whole rows fitting ~80 MB (G×S×1 KB per pair), rounded down to a power of 2.
   - **Rule 2b:** idea 4 only when Hkv ≥ BLU_VJ2_HSUM_MINKV (default 2), decided by shape only, which keeps packed == alone bit-identical.
   - **Switches:** BLU_VJ2_HSUM, _MINKV, _SECT, DKDV_F32.
   - **Messages:** printed only when idea 4 is OFF, one line per reason, once per process.
   - **Side table** in GQA_fwd_generic.cu, keyed by the plan's vj2_blocks pointer. Used so GqaChatPlan's by-value layout is unchanged.
   - The SFT trainer always runs packed rows. The dense HSUM variant `<false,false,true>` is exercised only by the test program.

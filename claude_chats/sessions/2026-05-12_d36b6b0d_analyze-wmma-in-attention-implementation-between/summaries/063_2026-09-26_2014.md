2. Key Technical Concepts:

   **Bug D.** The `exponent > 0x8E` clamp (the fp16 limit 127+15) in `float_to_bfloat16` turned every |x| ≥ 65,536 into Inf: 1,878,982,656 of 2^32 wrong. On the GPU, kernels templated on `OwnTensor::bfloat16_t` run the Types.h manual code.

   **GPU (device) paths now use NVIDIA intrinsics.** Each intrinsic selects its instruction per arch at compile time (`NV_IF_ELSE_TARGET` in cuda_bf16.hpp / cuda_fp16.hpp):

   | Conversion | Intrinsic | Instruction (SASS) |
   |---|---|---|
   | fp32→bf16 | `__float2bfloat16_rn` | F2FP.BF16 on sm_80+ (F2FP.BF16.PACK_AB on sm_80/86, .F32.PACK_AB from sm_89); NVIDIA software on sm_75 |
   | fp32→fp16 | `__float2half_rn` | F2FP / F2F.F16.F32 |
   | fp16→fp32 | `__half2float` | HADD2.F32 |
   | double→bf16 | `__double2bfloat16` | F2F.BF16.F64 on sm_90+, round-to-odd software below |
   | double→fp16 | `__double2half` | F2F.F16.F64 |
   | ints→bf16 | `__int2bfloat16_rn`, `__uint2bfloat16_rn`, `__ll2bfloat16_rn`, `__ull2bfloat16_rn` | I2F.BF16 on sm_90+; ru/rd/rz round-to-odd below |
   | ints→fp16 | `__int2half_rn` etc. | I2F.F16 |

   - bf16→fp32 stays a shift (SHF.L.U32) on every arch; PTX says `cvt.f32.bf16` gives an "unspecified NaN".
   - There is no C++ intrinsic for fp16↔bf16. Going through fp32 is exact; it was proven on the H200 against the direct `cvt.rn.bf16.f16` (0 differences).
   - GPU intrinsics cannot "fail" at runtime. Our bit code is NOT a GPU fallback: it is CPU-only (`#if defined(__CUDA_ARCH__)` intrinsic `#else` CPU code).

   **CPU (host) paths.**
   - fp16: F16C `_cvtss_sh` / `_cvtsh_ss` when `__F16C__` is defined (the library's .cpp files are built with -mf16c). NaN is mapped to 0x7FFF. The manual RNE code is the fallback (e.g. the nvcc host pass).
   - bf16: the bias trick `u += 0x7FFF + ((u>>16)&1)`, NaN→0x7FFF, no clamp.
   - double→bf16/fp16: round-to-odd into float using the hardware conversion (NVIDIA's host method), then one RNE. Boldo & Melquiond, IEEE Trans. Computers 57(4) 2008: ≥ 2 extra bits are enough. It needs flush-to-zero off.
   - int8/16 → through float (exact).
   - int32→bf16: static_cast<double> (exact), then round-to-odd (branch-free; it vectorizes).
   - int64→bf16: fits24 fast path (`static_cast<uint64_t>(v) + (1ull<<24) <= (1ull<<25)`), otherwise `int64_to_float_rto` (exact integer round-to-odd into float; branch-free sign trick).
   - all ints→fp16: through float (always one rounding: |v| ≥ 65520 → Inf either way).

   **Other facts.**
   - Figueroa 1995: the arithmetic operators computed in float are safe (p' ≥ 2p+2).
   - IEEE 754: roundTiesToEven is the default for binary formats.
   - CUDA's software NaN output is 0x7FFF; on the H200, fp32→bf16/fp16 NaN is 0x7fff.
   - `--use_fast_math` gives FMUL.FTZ and float→double FTZ in device float math.
   - fp32 holds every integer exactly up to 2^24 = 16,777,216 (≈1.7×10^7); bf16 up to 256, fp16 up to 2048, fp64 up to 2^53.

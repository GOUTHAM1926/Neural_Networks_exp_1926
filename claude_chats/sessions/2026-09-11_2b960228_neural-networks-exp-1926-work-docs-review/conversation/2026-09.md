## What you reported

3D tensor `[X, Y, Z]`, row-major. You reduce over **X and Z**, keep **Y**. Eigen's innermost loop runs over **X with stride Y·Z** (the huge jump), while **Z with stride 1** is the outer loop. PyTorch does the opposite — Z innermost. That's the whole bug.

## 1. TensorFlow sends this case straight to Eigen — no transpose

[reduction_ops_common.h:209-213](tensorflow/tensorflow/core/kernels/reduction_ops_common.h#L209-L213):

```cpp
} else if ((helper.ndims() == 3) && helper.reduce_first_axis()) {
  // Can be viewed as a reduction of a 3D tensor along 1st and 3rd dimensions.
  Functor::Reduce(ctx, helper.out<T,1>(&tmp_out), helper.in<T,3>(data),
                  constants.kZeroTwo, reducer);
}
```

`kZeroTwo = {0, 2}` ([:57-58](tensorflow/tensorflow/core/kernels/reduction_ops_common.h#L57-L58)). This is one of the six hardcoded fast cases — the `else` branch below it (`DoTranspose` + 2D→1D) never fires here. TF tensors are `Eigen::RowMajor` ([tensor_types.h:28](tensorflow/tensorflow/core/framework/tensor_types.h#L28)), so Z is the stride-1 dim.

## 2. Eigen picks GenericDimReducer, and it has no SIMD

With reduced dims `{0,2}` on rank 3 row-major: `ReducingInnerMostDims` is false (reduced dims aren't a contiguous suffix) and `PreservingInnerMostDims` is false (dim 2 *is* reduced) — both at [TensorReduction.h:584-585](eigen/unsupported/Eigen/src/Tensor/TensorReduction.h#L584-L585). So `coeff()` falls to the else at [:810](eigen/unsupported/Eigen/src/Tensor/TensorReduction.h#L810):

```cpp
internal::GenericDimReducer<NumReducedDims - 1, Self, Op>::reduce(...);
```

And `packet()` falls to the last else at [:849-852](eigen/unsupported/Eigen/src/Tensor/TensorReduction.h#L849-L852) — a scalar `for` loop calling `coeff()` PacketSize times. **No vectorization at all** on this path. That's a second finding beyond the traversal order.

## 3. Why the order comes out backwards

`m_reducedStrides` and `m_reducedDims` are filled in **input-dimension order** — [:639-650](eigen/unsupported/Eigen/src/Tensor/TensorReduction.h#L639-L650) and `DimInitializer` at [:61](eigen/unsupported/Eigen/src/Tensor/TensorReduction.h#L61). For `[X,Y,Z]` reducing `{0,2}`:

| slot | dim | stride |
|---|---|---|
| `m_reducedStrides[0]` | X | **Y·Z** |
| `m_reducedStrides[1]` | Z | **1** |

`GenericDimReducer` recurses from `DimIndex = NumReducedDims-1` down to `0` ([:131-150](eigen/unsupported/Eigen/src/Tensor/TensorReduction.h#L131-L150)), so **slot 0 is the innermost loop**. Innermost = X, stride Y·Z. Outer = Z, stride 1. Every single element access jumps Y·Z floats — cache line fetched, one value used, thrown away.

## 4. What PyTorch does instead

[TensorIterator.cpp:232-236](pytorch_source/aten/src/ATen/TensorIterator.cpp#L232-L236) — `reorder_dimensions()` sorts by **stride ascending**, reduced dims to the front (= fastest-moving):

```
// Sort the dimensions based on strides in ascending order with reduced dims
// at the front... strides[0] is the fastest moving dimension
```

Same shape: reduced dims X and Z go to the front, sorted by stride → **Z (stride 1) innermost, then X, then Y**. Written outermost-in: Y → X → Z. That is exactly the `Y--->X--->Z` you put in the title. It's chosen at runtime from the strides, not from a hardcoded shape case, so it can never come out backwards.

const int x = group / extent_z_;

`group` is the position inside a segment. Your bug lives entirely in the CPU path, where Eigen walks X (stride Y·Z) fastest.

## First: what is `intra_op`?

TensorFlow uses threads two different ways:

- **`intra_op`** = how many threads work **inside one operation**. One `reduce_sum` split across 8 threads = `intra_op` 8.

## Why so slow — the simple reason

The computer does not fetch one number at a time from memory. It grabs a **chunk** (a cache line, 64 bytes = 16 floats).

So if you read numbers that sit **next to each other**, one fetch gives you 16 useful numbers. Fast.

If you read numbers that are **far apart**, every fetch gives you 1 useful number and 15 wasted. You throw away 15/16 of everything you fetch.

In your case, the Z direction is the one where numbers sit next to each other. **Eigen loops over X on the inside instead of Z.** So it jumps far every single step. That's the whole bug.

PyTorch always puts the close-together direction on the inside. That is why PyTorch stays fast no matter which direction you pick — 0.17, 0.12, 0.37 ms. Flat. TF goes 4.75, 0.15, 0.58. One of them falls off a cliff.

---

## 3. Where it comes from

For a row-major `[X,Y,Z]` reducing `{0,2}`, `TensorReduction.h:639-650` fills `m_reducedStrides` in input dimension order:

```
m_reducedStrides[0] = Y*Z    (X)
m_reducedStrides[1] = 1      (Z)
```

`GenericDimReducer` (`TensorReduction.h:131-150`) recurses from `NumReducedDims-1` down to `0`, so slot 0 is the innermost loop, which is X striding Y*Z per element, and Z the stride-1 axis ends up as the outer loop, meaning every element read pulls a new cache line and uses one value out of it.

Two more things on the same path, `ReducingInnerMostDims` and `PreservingInnerMostDims` are both false so `packet()` drops into the last `else` at `TensorReduction.h:849-852` and just calls `coeff()` PacketSize times, meaning no vectorization, and `BlockAccess` is false on the reduction evaluator (`TensorReduction.h:572`) so there's no tiled path either.

For comparison, PyTorch's `TensorIterator::reorder_dimensions` (`TensorIterator.cpp:232-236`) sorts dimensions by stride ascending, so the stride-1 axis is innermost no matter which axes are reduced, which is why its three columns above are flat and TF's aren't.

## 4. GPU is fine

Just to be clear on scope, this is CPU only, `ReduceImpl` in `reduction_gpu_kernels.cu.h` has a branch for `in_rank==3 && out_rank==1 && axes=={0,2}` that calls `Launch3DXZReduction`, and that uses CUB `DeviceSegmentedReduce` with a gather iterator whose index advances along Z first, so reads are coalesced and the order is right, no Eigen. Only the `ReduceEigenImpl` path in `reduction_ops.h:53-58` is affected.

Checked the actual code. Your description is right, and there are three things in it worth knowing.

## How the lookup runs

[EmbeddingKernels.cu](../sft_research/BluTrain/Tensor-Implementations/src/Kernels/cuda/embedding/EmbeddingKernels.cu) — one thread per output element, 2D grid:

```
c = blockIdx.x * blockDim.x + threadIdx.x   // which of the 2304 columns
n = blockIdx.y * blockDim.y + threadIdx.y   // which of the 32,768 positions
```

Block is `(32, 8)`, so one block covers 32 columns × 8 positions. Your shape gives a grid of `2304/32 = 72` by `32768/8 = 4096` — about 295k blocks, 75.5M threads, one per output float.

Each thread reads its position's token id, then copies one element:

```cpp
output[n * C + c] = weight[tok * weight_stride_row + c * weight_stride_col];
```

No shared memory, no reuse. It's a pure gather — 32,768 rows pulled out of the table in whatever order the token ids happen to be. Reads of the table are scattered, writes to the output are perfectly sequential.

## 1. fp32 and bf16 take completely different kernels

This is the big one for your case 1 vs case 2.

| table dtype | kernel | per thread |
|---|---|---|
| **fp32** | `embedding_forward_kernel_vectorized` | 4 × `float4` = **64 bytes** |
| **bf16** | `embedding_forward_kernel_optimized<__nv_bfloat16>` | 1 element = **2 bytes** |
| fp16 | same scalar one | 2 bytes |

The vectorized kernel is **fp32 only** — it's not a template, it's hardcoded `const float*`. bf16 and fp16 fall to the scalar template.

So the bf16 path moves half the bytes but issues **32× more load instructions** per row. The fp32 one also does a warp broadcast so only lane 0 reads the token id and `__shfl_sync` spreads it to the other 31 lanes. The bf16 one has every single thread re-read `indices[n]` from memory.

fp32 needs `C % 4 == 0`, contiguous weight, and 16-byte alignment to vectorize. Your C is 2304, divisible by 4, so it does.

## 2. Your pad positions copy a real row — they are not zeroed

The kernel has a padding branch:

```cpp
if (tok == (uint16_t)padding_idx) { output[n*C + c] = T{}; return; }
```

But the trainer never turns it on. [gpt2_fmha_ddp.cpp:136](../sft_research/BluTrain/gpt2_fmha_ddp.cpp#L136) calls:

```cpp
Tensor out = autograd::embedding(weight, indices);
```

Two arguments. The third defaults to **`padding_idx = -1`** ([EmbeddingOps.h:17](../sft_research/BluTrain/Tensor-Implementations/include/autograd/operations/EmbeddingOps.h#L17)), and `(uint16_t)(-1)` is 65535, which no token ever equals. So the branch never fires.

Your 300 pad positions get a genuine copy of that row's vector, exactly as you described. That's fine as long as the loss masks them — which yours does — but it means pad rows also collect gradient in the backward pass unless something else stops them.

## 3. Indices get squeezed to `uint16_t` on the way in

```cpp
Tensor indices_u16 = (indices_gpu.dtype() == Dtype::UInt16)
    ? indices_gpu : indices_gpu.as_type(Dtype::UInt16);
```

Your indices are Int64 in the trainer, so every forward pass silently casts them down. `uint16_t` tops out at 65,535. GPT-2's 50,257 fits, so nothing is broken today — but the cap is 65,535 and there's no check, so a larger vocab would wrap around and read the wrong rows with no error.

There's also a quiet failure mode in the kernel: `if (tok >= V) return;` just *returns* without writing. That leaves whatever was in the output buffer, rather than raising anything. The CPU path throws properly on out-of-range; the GPU path doesn't.

## Worth a look

The bf16 case is doing 32× the loads it needs to. Templating the vectorized kernel over the type — `float4` for fp32, and 8 bf16 in the same 16 bytes — would close it. Given bf16 is the direction you're moving, that's probably the one to measure.
